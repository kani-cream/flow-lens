# Flow Lens v0.2 Implementation Specification

## 1. Purpose

v0.1 discovers calls inside branches and loops but does not represent the
structure: it marks such calls as conditional and discloses that control flow is
simplified. v0.2 makes the structure itself part of the map.

> The map should show not only which calls exist, but which of them are
> alternatives, which repeat, and where the paths come back together.

`PLAN.md` §17 defines the scope. This document fixes the semantics and the
observable behavior, the way `V0.1_SPEC.md` did for v0.1.

---

## 2. Scope

### In scope

| Construct | Java | Kotlin | Go |
|---|---|---|---|
| `if` / `else` | yes | yes (`if` expression) | yes |
| multi-way branch | `switch` (statement and expression) | `when` | `switch`, type switch |
| channel select | — | — | `select` |
| loops | `for`, enhanced `for`, `while`, `do`-`while` | `for`, `while`, `do`-`while` | `for`, `for`-`range` |
| exception handling | `try`/`catch`/`finally` | `try`/`catch`/`finally` | — |
| termination | `return`, `throw` | `return`, `throw` | `return` |

Also in scope: branch labels, condition summaries, reconvergence after a
structure, loops as containers rather than duplicated chains, and narrowing the
`controlFlowIncomplete` disclosure to what is genuinely still unmodelled.

### Out of scope (later milestones)

- **Reachability.** A `return` inside a branch does not remove the events that
  follow the structure from the map. v0.2 shows structure, not path feasibility.
- **Java `switch` fall-through** between cases without `break`.
- **Labelled `break` / `continue`** as edges back to a specific structure.
- **Exception routing**: which `throw` a given `catch` can receive.
- **Go `select` runtime semantics**: which case a scheduler picks, blocking
  behavior, or channel direction.
- **Short-circuit operands as branch structure**: `a() && b()`, `a ?: b()`, and
  `a?.b()` keep the v0.1 conditional marker instead of becoming a structure.
- Condition evaluation, constant folding, or branch elimination.

## 3. Model

`FlowNode` gains branches; a structural node owns one or more labelled branches,
each of which is an ordered list of events:

```text
FlowNode
- ...v0.1 fields
- branches[]        // empty for a call
- structureSummary? // source-derived, short, for display only

FlowBranch
- kind              // THEN, ELSE, CASE, DEFAULT, BODY, TRY, CATCH, FINALLY
- label?            // source-derived, short: a case value, an exception type
- events[]
```

Rules:

1. A frame's `events` list stays flat; nesting lives on the node. A structural
   node is one event in its parent's sequence, exactly like a call.
2. Structural nodes use the existing kinds `CONDITION`, `SWITCH`, `LOOP`, `TRY`,
   `RETURN`, `THROW`.
3. `structureSummary` and `FlowBranch.label` carry short source-derived text so
   the reader can tell branches apart. They are display data: they are never
   logged (guardrails §13), and long text is truncated at the source.
4. Every structural node counts against the semantic-node budget, as any other
   persistent node does (`PLAN.md` §11).
5. Structural nodes never consume callable depth (`V0.1_SPEC.md` §9).
6. Cycle detection is unchanged: it is about callable paths, not structures.

---

## 4. Evaluation order

Code that runs before a structure is entered stays *before* the structural node
in the parent sequence; code that runs as part of the structure lives inside it.

```text
if (check()) { charge(); } else { skip(); }
save();
```

```text
check()          ← evaluated first, ordinary event
◆ CONDITION      ← structure
   THEN: charge()
   ELSE: skip()
save()           ← after reconvergence
```

Per construct:

- **if**: condition calls precede the node. Java/Kotlin/Go init statements also
  precede it.
- **switch / when**: subject calls precede the node. Each case is a branch; a
  case label's source text becomes the branch label.
- **loops**: anything evaluated once before the loop (a `for` initializer, the
  iterable of a `for`-each, a Go range expression) precedes the node. Anything
  evaluated per iteration (condition, update) belongs inside the body branch, in
  source order, so a repeated call appears once inside the container rather than
  duplicated outside it.
- **do-while**: the body precedes the condition inside the container, and the
  container records that the body runs at least once.
- **try**: the resource list precedes the node; `try`, each `catch`, and
  `finally` are branches.
- **return / throw**: the expression's calls precede the terminator node.

## 5. Conditional marking

v0.1 marks a call conditional when it may not execute. With structure
represented, the branch itself carries that meaning, so:

- a call inside a `THEN`, `ELSE`, `CASE`, `DEFAULT`, `BODY`, or `CATCH` branch is
  **not** marked conditional — its section already says so;
- a call whose conditionality is *not* expressed by an enclosing structure keeps
  the marker: short-circuit operands, elvis, and safe calls;
- a call in a `TRY` or `FINALLY` branch is not conditional (both run).

This removes the double signal and keeps the marker meaningful for exactly the
cases v0.2 does not model.

---

## 6. `controlFlowIncomplete`

The result stays `controlFlowIncomplete = true` only when the analyzer met
something it did not represent:

- a short-circuit, elvis, or safe-call operand;
- a `break` or `continue`;
- Java `switch` fall-through between non-empty cases;
- any construct an analyzer skipped.

A method whose control flow consists of represented structures no longer carries
the disclosure. This is the visible payoff of the milestone: the warning now
means something specific instead of appearing on every branch.

Reachability remains out of scope, so a `return` inside a branch does not clear
the disclosure for the events after it — see §9.

## 7. Visual grammar

Owner decision (2026-08-18): branches render as **stacked labelled sections**
inside one container, not as side-by-side columns.

The design mockup in `VISUAL_DESIGN.md` §13 shows a left/right fork. A fork needs
at least two card widths, and the tool window is routinely narrower than that, so
every `if` would force horizontal scrolling and a `switch` with several cases
would be unusable. Stacking satisfies the section's stated requirements — a
distinct shape for the condition, visible branch labels, visible reconvergence,
and a summarized condition — at one card width, and scales to any number of
branches and to nesting.

```text
  │
  ▼
╭─ ◆ flag ?  ─────────────────╮
│  THEN                        │
│    charge()            D0    │
│  ELSE                        │
│    skip()              D0    │
╰──────────────────────────────╯
  │   ← reconvergence
  ▼
save()                    D0
```

Requirements:

- the structural header uses a shape and glyph distinct from a call card;
- every branch section is labelled, and the label is the source text where one
  exists (`case 1`, `catch (IOException)`);
- the connector leaving the container expresses reconvergence: the sequence
  continues after the structure;
- a loop container marks that its body repeats;
- a `do`-`while` container marks that its body runs at least once;
- `return` and `throw` render as terminal markers that visibly end their branch;
- a structure with an empty branch still shows the branch, so "this case does
  nothing" is distinguishable from "this case is missing";
- containers nest, and a nested structure is laid out like any other event
  inside its branch.

## 8. Acceptance cases

| # | Case | Expected |
|---|---|---|
| A | `if (c()) a(); else b(); d();` | `c()`, CONDITION[THEN: a, ELSE: b], `d()` |
| B | `if (c()) a(); d();` | CONDITION with only THEN; `d()` after it |
| C | `switch (s()) { case 1: a(); break; default: b(); }` | `s()`, SWITCH[CASE "1": a, DEFAULT: b] |
| D | Kotlin `when (s()) { 1 -> a(); else -> b() }` | SWITCH with the same shape |
| E | `for (int i = 0; i < n(); i++) { a(); }` | LOOP[BODY: n, a] — `n()` appears once, inside |
| F | `for (T x : items())` | `items()` before the LOOP node |
| G | `do { a(); } while (c());` | LOOP[BODY: a, c] marked as running at least once |
| H | `try { a(); } catch (E e) { b(); } finally { c(); }` | TRY[TRY: a, CATCH "E": b, FINALLY: c] |
| I | `return f();` | `f()` then RETURN |
| J | `throw new E(g());` | `g()`, constructor, then THROW |
| K | Go `switch x := s(); x { case 1: a() }` | init and subject before SWITCH |
| L | Go `select { case <-ch: a() }` | SWITCH-shaped node marked as a select |
| M | Nested `if` inside a loop body | LOOP[BODY: CONDITION[...]] |
| N | A call inside a branch | not marked conditional |
| O | `a() && b()` | `b()` still marked conditional; result stays incomplete |
| P | A method whose only control flow is an `if` | `controlFlowIncomplete = false` |
| Q | An empty branch (`case 1: break;`) | branch present and visibly empty |
| R | Node budget exhausted inside a branch | LIMIT marker, result TRUNCATED |

## 9. Known limitations introduced by v0.2

To be recorded in `KNOWN_LIMITATIONS.md` when implemented:

1. Structure is not reachability: events after a structure are shown even when
   every branch returns or throws.
2. Java `switch` fall-through is not represented; each case reads as independent.
3. `break` and `continue` are not shown as edges.
4. A `catch` branch is not connected to the `throw` that could reach it.
5. Go `select` shows its cases, not its runtime choice or blocking behavior.
6. Loop containers do not express iteration counts or termination conditions
   beyond the summary text.
