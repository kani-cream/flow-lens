## 3. Planning-document conflicts recorded

`README.md` requires recording conflicts rather than silently choosing an
interpretation.

1. **`Analyze from Here`** appears in `VISUAL_DESIGN.md` §7/§18 as a source
   action, while `PLAN.md` §17 schedules "Analyze from selected node" for v0.3
   and `V0.1_SPEC.md` §18 lists only Open Target / Open Call Site.
   **Resolution:** treated as v0.3. Not implemented in v0.1; the canvas keeps
   the seam (selection already exposes the target declaration) so promoting a
   node to a new root stays a small change later.

2. **Depth-limit representation.** `V0.1_SPEC.md` §9 says crossing beyond the
   limit "produces a visible `LIMIT` event", while `PLAN.md` §11 reserves the
   node budget's final slot for a `LIMIT` node and the 100-node budget must not
   be consumed by one marker per blocked call.
   **Resolution:** the blocked call keeps its own card (so the user sees *which*
   call was not entered) and the canvas renders an explicit depth-limit
   continuation marker beneath it with the "increase depth" hint. The budget's
   reserved `LIMIT` node remains dedicated to node-budget truncation. No
   semantic information is lost and a 100-node analysis cannot be flooded by
   limit markers.

3. **Conditional execution vs ordering.** `V0.1_SPEC.md` §13.5 forbids ordinary
   certain connectors implying an unproven path, but the model's ordering
   dimension describes relative order, not whether a call executes.
   **Resolution:** conditional calls keep their language-guaranteed
   `orderingStatus` and carry a `flowlens.conditional` metadata marker; the
   canvas renders their connector with the same non-certain treatment used for
   non-deterministic ordering. `controlFlowIncomplete` continues to disclose the
   simplification at result level. A first-class branch model belongs to v0.2.
