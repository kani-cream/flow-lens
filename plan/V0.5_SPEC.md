# Flow Lens v0.5 Implementation Specification

## 1. Purpose

A callable body handed to another callable — a lambda, a Kotlin trailing lambda,
a Go function literal — is dropped from the map without a word.

```kotlin
fun start() {
    launch { charge() }     // charge() is not on the map, and nothing says so
    save()
}
```

The reader sees `save()` and concludes that is the flow. It is not: `charge()`
runs too, at a time the analyzer cannot state. This is the same failure v0.2
closed for branches — a map that omits without disclosing — and it is why this
milestone is a correctness pass rather than a feature.

> Flow Lens may say "this runs at a time I cannot determine". It may not say
> nothing at all.

`PLAN.md` §17 lists async work under v0.5+; the owner scoped v0.5 to this alone
on 2026-08-18, and froze feature growth after it.

---

## 2. Scope

### In scope

| | |
|---|---|
| Callback bodies | A lambda or function literal passed to a call becomes a visible event owning its body. |
| Execution timing | Each such body says whether it runs during the call, later, concurrently, or at a time the analyzer cannot determine. |
| Ordering honesty | A body that does not run in place is not presented as the next step. |
| Go parity | `go func() { … }()` and `defer func() { … }()` bodies become visible, like any other deferred body. |

`ExecutionMode.ASYNC` and `OrderingStatus.APPROXIMATE`/`UNSPECIFIED` already
exist in the model, are already rendered by the canvas, and are already carried
by both exports — **nothing has ever produced them**. This milestone populates
dimensions the tool already knows how to show, which is why it needs no new
visual grammar.

### Out of scope

- **Search, filtering, path highlighting**; **flow comparison and Git overlay**;
  **reverse/caller analysis**; **framework-aware resolution**. Deferred by the
  owner on 2026-08-18 to v1.x, so that v1.0 is a stabilization release rather
  than a wider one.
- **Deciding when an unknown callback actually runs.** Where the analyzer cannot
  justify a timing, it says so; it does not guess.
- **Concurrency correctness**: races, happens-before, thread confinement.
  Flow Lens shows what may run, never whether it is safe.
- **A lambda that is not passed to a call** — stored in a field, returned,
  assigned to a variable. Its invocation site is elsewhere, and following it
  would be reverse analysis.
- **Channel topology for Go**: which goroutine receives what. `select` already
  renders as a structure (v0.2); this milestone adds the goroutine's *body*, not
  its communication graph.

## 3. The model

A callback body becomes one event owning a frame, exactly as a call does.

```text
FlowNodeKind
- ...existing kinds
- CALLBACK          // a callable body handed to another callable
```

Rules:

1. A `CALLBACK` event is emitted **after** the call it was passed to, because the
   call is what receives it. Its own body is a child frame, expandable like any
   other.
2. It counts against the node budget and consumes one depth level, like every
   other callable body (`PLAN.md` §11, `V0.1_SPEC.md` §9). A callback is a
   callable body; nothing about it justifies an exemption.
3. It carries the **execution mode** and **ordering status** of §4. Those two
   fields are the whole point: without them a callback body is just more flow,
   and the map would be claiming something it cannot support.
4. Cycle detection treats a callback body by the callable that owns it, so a
   recursive callback is caught like any other recursion.
5. A call may receive several callbacks. Each becomes its own event, in argument
   order.

## 4. Timing

The one question that matters: **when does this body run?** Four answers, and the
analyzer must be able to justify whichever it gives.

| Answer | Execution mode | Ordering | When it is used |
|---|---|---|---|
| During the call, then the flow continues | `SYNC` | `DETERMINISTIC` | the language or a documented API guarantees in-place invocation |
| Concurrently, at an unspecified time | `ASYNC` | `UNSPECIFIED` | a documented asynchronous API |
| Concurrently, Go's own construct | `GOROUTINE` | `UNSPECIFIED` | `go f()` |
| When the frame returns | `DEFERRED` | `UNSPECIFIED` | `defer f()` |
| **Cannot be determined** | `UNKNOWN` | `UNSPECIFIED` | **everything else** |

**`UNKNOWN` is the default.** A callback is only called synchronous or
asynchronous when something says so; otherwise the map states that the timing is
not known. That is the difference between this milestone and a heuristic.

### 4.1 What justifies `SYNC`

- **Kotlin**: the receiving function is `inline` and the parameter is not
  `noinline`. Such a lambda cannot escape the call, so it runs during it. A
  `kotlin.contracts` `callsInPlace` declaration counts as well where present.
- **Java**: the receiving method is on the documented in-place list (§4.3).
- A `suspend` function call is **not** a callback at all — it is an ordinary
  call that happens to suspend. It stays `SYNC`, because the coroutine resumes
  where it left off and the next statement still runs after it.

### 4.2 What justifies `ASYNC`

The receiving method is on the documented asynchronous list (§4.3).

### 4.3 The lists

Small, explicit, and documented as a limitation rather than presented as
complete.

**In place (Java)**: `Iterable.forEach`, `Map.forEach`, `Optional.map`,
`Optional.ifPresent`, `Optional.orElseGet`, `Stream.map`, `Stream.filter`,
`Stream.forEach`, `Map.computeIfAbsent`, `Map.computeIfPresent`.

**Asynchronous (Java)**: `ExecutorService.submit`, `ExecutorService.execute`,
`ScheduledExecutorService.schedule`, `CompletableFuture.supplyAsync`,
`CompletableFuture.runAsync`, `CompletableFuture.thenApplyAsync`,
`CompletableFuture.thenAcceptAsync`, `CompletableFuture.thenRunAsync`,
`Thread(Runnable)`.

**Asynchronous (Kotlin)**: `kotlinx.coroutines.launch`,
`kotlinx.coroutines.async`.

**In place (Kotlin)**: `withContext` and `runBlocking` — both run the block
before the next statement, on another dispatcher or thread. The map is about
order, not about which thread.

Anything not listed and not `inline` is `UNKNOWN`. The lists live in one place
per language and are expected to grow.

## 5. What the reader sees

No new visual grammar; the existing states carry it.

```text
start()
  submit()                  D0        ← the call
  ⇢ callback of submit()    D1  async ← the body it was handed
      charge()              D1
  save()                    D0
```

Requirements:

1. A callback event is **visibly not an ordinary step**: its incoming connector
   is dashed, which the canvas already does for anything whose ordering is not
   deterministic.
2. It names what it is a callback **of**, so the reader can tell two callbacks of
   one call apart.
3. Its timing is stated in words — in the card's tooltip, in the details panel,
   and in both exports — never by position alone.
4. A callback whose timing is `UNKNOWN` says so explicitly. Silence would mean
   the reader supplies their own assumption.
5. `save()` still follows `submit()`, not the callback: reconvergence is
   unchanged, and a callback is not on the synchronous path.

## 6. Disclosure

`controlFlowIncomplete` is about control flow the analyzer did not represent
(`V0.2_SPEC.md` §6). Callback bodies are now represented, so they no longer
contribute to it.

What replaces it is per-node: an `UNKNOWN` timing on the callback itself. A run
whose callbacks are all justified says nothing extra; a run with an unknown
timing shows it on the card that has it.

The status area's "why the map stops" summary (`V0.3_SPEC.md` §7.3) gains one
line: how many callbacks have an undetermined timing, so a reader can find them.

## 7. Acceptance cases

| # | Case | Expected |
|---|---|---|
| A | `executor.submit(() -> charge())` | callback event after `submit()`, mode async, body contains `charge()` |
| B | Kotlin `launch { charge() }` | callback event, mode async, ordering unspecified |
| C | Kotlin `list.forEach { charge() }` | callback event, mode sync, ordering deterministic (inline) |
| D | Kotlin `withContext(io) { charge() }` | mode sync — it runs before the next statement |
| E | A call to a `suspend fun` | an ordinary call, mode sync, no callback event |
| F | Java `list.forEach(x -> charge())` | mode sync, from the in-place list |
| G | A lambda passed to a project method not on any list | mode unknown, and the card says so |
| H | Go `go func() { charge() }()` | callback event, mode goroutine, body visible |
| I | Go `defer func() { cleanup() }()` | callback event, mode deferred |
| J | Two lambdas in one call | two callback events, in argument order |
| K | A callback body at the depth limit | depth marker, body not entered, like any callable |
| L | A callback body exhausting the node budget | LIMIT marker, result truncated |
| M | A callback that calls its own enclosing callable | cycle, not infinite recursion |
| N | A lambda stored in a variable, never passed to a call | not a callback event; nothing invented |
| O | The step after a call with a callback | still follows the call, not the callback |
| P | A flow whose callbacks are all justified | no undetermined-timing line in the status area |
| Q | A flow with an unknown-timing callback | counted in the status summary, and the count leads to the card |
| R | Export of a flow with callbacks | timing stated in words in both formats |
| S | A nested callback (a lambda inside a lambda) | nested frames, each with its own timing |
| T | A callback body with a branch inside it | v0.2 structures render normally inside it |

## 8. Known limitations introduced by v0.5

To be recorded in `KNOWN_LIMITATIONS.md` when implemented:

1. Timing comes from a short list of documented APIs plus Kotlin's `inline`
   rule. A project's own asynchronous helper is `UNKNOWN` until its API is
   recognized, which is honest but not helpful.
2. `UNKNOWN` is common in Java, which has no language-level signal that a lambda
   runs in place.
3. A callback that is stored and invoked elsewhere is not followed. Finding its
   invocation site is reverse analysis, deferred to v1.x.
4. Flow Lens shows that bodies may run concurrently. It says nothing about
   whether that is safe: no races, no happens-before, no thread confinement.
5. Go channel topology is unchanged: `select` renders as a structure, and a
   goroutine's body is now visible, but which goroutine receives what is not
   modelled.
6. Ordering between two asynchronous callbacks is unspecified, and the map draws
   them in source order because it must draw them somewhere. Position is not a
   claim about sequence — the same rule as `VISUAL_DESIGN.md` §19.
