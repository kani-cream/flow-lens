# Flow Lens v0.3 Implementation Specification

## 1. Purpose

v0.1 and v0.2 made one analysis good. v0.3 makes the tool usable across a
working day: the flows a developer cares about survive the session, the ones
they looked at recently are one click away, the functions they are tracking are
marked wherever they appear, and a running analysis says what it is doing.

> Everything here is about returning to work, not about analyzing it better.

`PLAN.md` §17 defines the scope. This document fixes the semantics and the
observable behavior, the way `V0.2_SPEC.md` did for v0.2.

---

## 2. Scope

### In scope

| Feature | What it is |
|---|---|
| Flow Pins | A persistent mark on a **callable**. Any flow containing it shows the mark; the pin list analyzes it directly. |
| Saved Flows | A named, persistent **entry point** plus the limits it was analyzed with. Opening one re-runs the analysis. |
| Recent analyses | An automatic, capped list of recently analyzed entry points. Same re-run behavior, no naming. |
| Analyze from selected node | Promote the selected card's target to the new root. |
| Progress and status | Name the callable being analyzed, show budget consumption, and summarize why the map stops where it does. |

`PLAN.md` §17 lists "persistent saved entry points" separately from "Saved
Flows". They are the same feature: a saved flow *is* a persisted entry point.
Recorded here rather than built twice.

### Out of scope (later milestones)

- **Persisting analysis results.** A result describes one source revision and is
  stale the moment the file changes (`PLAN.md` §18.18). Saved Flows and Recents
  store the entry point and re-run; they never restore a stale picture.
- **Sharing**: exporting a flow, or moving pins between machines (v0.4).
- **Following a symbol through a refactor.** Identity is best-effort, per
  `KNOWN_LIMITATIONS.md` §17, and §8 below says what happens when it fails.
- **Pinning a node rather than a callable.** A pin marks a function, not one
  call site of it. Two calls to a pinned function are both marked.
- **Cross-project pins.** Everything here is project-scoped.

## 3. Durable identity

`REPO_LENS_LESSONS.md` §3.8 forbids line or offset as the sole durable identity.
v0.3 uses, in order:

1. **`FlowSymbol.key`** — language, qualifier, name, and parameter types, which
   the analyzers already produce (`java:PaymentService#charge(int)`). This is the
   identity that is stored and compared.
2. **Project-relative file path** — where to look for that key. Stored so the
   lookup does not need a global index per language.
3. **Source offset** — never stored as identity. A live session keeps a smart
   pointer, as it already does for navigation.

Resolving a stored entry means: open the file, enumerate the callables the
analyzer supports, and take the one whose key matches. That works for all three
languages through the existing `describeCallable`, without a language-specific
lookup API.

A stored entry therefore survives:

- editing anywhere in the file, including above the declaration;
- moving the declaration within its file;
- any change that does not alter the file path or the signature.

It does not survive a rename, a signature change, or a moved file. §8 says what
the user sees when that happens: a missing entry says so and is never silently
resolved to a different symbol.

## 4. Flow Pins

A pin marks a callable as one the developer is tracking.

Rules:

1. A pin stores the symbol identity of §3 and the display fields needed to list
   it without opening the file (display name, container, language).
2. Pins are project-scoped and survive restart.
3. **Any card whose target is pinned is marked**, in every flow, at every depth,
   including inside a branch section. The mark is a card state like the others:
   a distinct glyph, never colour alone (`VISUAL_DESIGN.md` §21).
4. The entry of a flow is marked too when the entry itself is pinned.
5. Pinning is available wherever a callable is selected: the canvas context
   menu, a keyboard shortcut, and the pin list.
6. Pinning is idempotent; pinning a pinned callable unpins it.
7. The pin list shows every pin and analyzes one on activation.
8. A pin whose declaration can no longer be found stays in the list, marked as
   unresolved, and says so rather than disappearing.

Pins do not affect analysis. They change nothing about traversal, limits, or
the model — a pinned function is analyzed exactly like any other. This keeps the
mark a reading aid rather than a hidden setting.

## 5. Saved Flows and Recent analyses

Both store an entry point and re-run it. They differ in who creates them and
whether they are kept.

| | Saved Flow | Recent |
|---|---|---|
| Created by | the user, explicitly | every analysis, automatically |
| Named | yes, defaulting to the symbol | no |
| Kept | until deleted | until evicted by newer entries |
| Limits | those of the run it was saved from | those of the run |
| Cap | none | 10 |

Rules:

1. Saving stores the symbol identity, the file path, the name, and the
   `FlowLimits` snapshot the analysis used. Opening restores all of it, so a
   flow saved at depth 5 re-runs at depth 5 even if the current setting differs.
2. A recent entry is written when an analysis reaches a terminal state, not when
   it starts, so a cancelled exploration does not push out real work.
3. Re-analyzing the same entry moves it to the top rather than duplicating it.
4. Opening a saved flow or a recent starts a normal analysis: the same progress,
   the same cancellation, the same staleness rules.
5. A saved flow whose declaration cannot be found reports that and stays in the
   list. It is never silently resolved to another symbol.
6. Deleting a saved flow is immediate and needs no confirmation; it deletes a
   bookmark, not work.

## 6. Analyze from selected node

The selected card's resolved target becomes the new root.

Rules:

1. Available only when the selection has a target declaration that could be
   analyzed — the same condition that already decides whether a call is
   expandable. An external, unresolved, or built-in target offers nothing to
   analyze and the command is disabled rather than failing.
2. It starts a new analysis, with the current settings, exactly as if the caret
   had been placed in that declaration. The previous result is replaced, as any
   new analysis replaces it (`REPO_LENS_LESSONS.md` §3.6).
3. The new root's depth is 0. Promoting a node discards the context it came
   from — that is the point of the command — and the map must not imply
   otherwise by keeping the old depth labels.

This resolves the conflict recorded in `V0.1_TASKS.md` §1: `VISUAL_DESIGN.md`
§7/§18 listed `Analyze from Here` as a source action while `PLAN.md` §17
scheduled it for v0.3. It lands here, as the resolution predicted.

## 7. Progress and status

Three changes, all about telling the truth about a run in progress.

### 7.1 Name what is being analyzed

The stage line says which callable the run is working on, not only that it is
working on child frames. It updates per frame, from the same event that already
carries the counters.

The name is a display symbol, so it never reaches a log
(`IMPLEMENTATION_GUARDRAILS.md` §13) — the counters continue to be what is
logged.

### 7.2 Budget consumption, not a progress bar

An analysis explores; the total is unknown until it finishes. A bar filling
toward "done" would be a guess presented as fact.

What is knowable is how much of the **node budget** has been consumed, and that
is what the bar shows. It is labelled as budget usage, and a full bar means the
result is about to be truncated — which is exactly the moment the user wants to
notice, because it means raising the limit would show more.

The owner asked for a bar with this caveat stated; this is the honest form of it.

### 7.3 Why the map stops where it does

When a run finishes, the status area summarizes the reasons the map has the
shape it has, as counts:

- calls not entered because of the depth limit;
- calls that could not be resolved;
- calls outside the project;
- calls into a cycle;
- whether the node budget truncated the run.

Each count is actionable: activating one selects the first such card on the
canvas, so the summary is a way into the map rather than a report about it.

A count of zero is not shown. A run with nothing to explain shows nothing, which
is what makes the presence of a line meaningful.

## 8. When a stored entry cannot be found

The single rule, from `KNOWN_LIMITATIONS.md` §17: **surface it, never guess.**

- The list entry stays and is visibly marked unresolved.
- Activating it explains that the declaration was not found and does not start
  an analysis.
- No fuzzy matching, no nearest-name fallback, no "did you mean". A pin that
  quietly moved to a different function would make every future reading of that
  mark untrustworthy.
- The user can delete it, which is the only repair v0.3 offers.

## 9. Persistence

| State | Scope | Where |
|---|---|---|
| Pins | project | project-level component |
| Saved Flows | project | project-level component |
| Recents | project | project-level component |

Rules:

1. Stored paths are **project-relative**. An absolute path would leak the
   machine layout into a file that is often committed
   (`IMPLEMENTATION_GUARDRAILS.md` §13).
2. Stored state contains symbol identities and paths only: never source text,
   never an analysis result.
3. Reading malformed or partial state must not fail the tool window. An entry
   that cannot be understood is dropped, not thrown.

## 10. Acceptance cases

| # | Case | Expected |
|---|---|---|
| A | Pin a callable, analyze an unrelated flow that reaches it | the card is marked |
| B | Pin a callable that appears twice in one flow | both cards are marked |
| C | Pin a callable that appears inside a branch section | the card is marked there too |
| D | Pin the entry, re-analyze | the entry is marked |
| E | Pin, then pin again | unpinned |
| F | Restart the IDE | pins, saved flows, and recents survive |
| G | Save a flow at depth 5, change the setting to 2, open the saved flow | it re-runs at depth 5 |
| H | Analyze A, then B, then A again | recents are A, B — A at the top, no duplicate |
| I | Cancel an analysis | no recent entry is written |
| J | Recents exceed the cap | the oldest is evicted |
| K | Rename a pinned function, open the pin | reported unresolved; no analysis starts |
| L | Move a saved flow's file, open it | reported unresolved; the entry stays in the list |
| M | Analyze from a selected project-local call | that callable becomes the root at depth 0 |
| N | Analyze from a selected external or unresolved call | the command is disabled |
| O | A run in progress | the stage names the callable being analyzed |
| P | A run approaching the node budget | the bar approaches full; truncation is not a surprise |
| Q | A finished run with depth-limited and unresolved calls | both are counted in the summary |
| R | Activating a summary count | the first matching card is selected on the canvas |
| S | A finished run with nothing to explain | no summary lines |
| T | Malformed stored state | the tool window still opens; bad entries are dropped |

## 11. Known limitations introduced by v0.3

To be recorded in `KNOWN_LIMITATIONS.md` when implemented:

1. A stored entry does not survive a rename, a signature change, or a moved
   file. It is reported unresolved rather than followed.
2. A pin marks a callable, not a call site: every call to a pinned function is
   marked, and there is no way to mark one of them.
3. Overloads are distinguished by parameter types as written, so a change to a
   parameter type breaks the identity even when the code is otherwise the same.
4. Recents are capped and unordered beyond recency; there is no search.
5. The budget bar describes budget consumption, not remaining work, because the
   total is not knowable during exploration.
6. Pins and saved flows are project-scoped and not shareable in v0.3.
