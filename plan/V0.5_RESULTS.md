## 2. What v0.5 added

- **`FlowNodeKind.CALLBACK`**, a body handed to a call. It owns a frame the way
  a call does — that is what makes the body enterable — but has no dispatch,
  because there is nothing to choose between.
- **A timing per callback**, carried on the two dimensions that already existed:
  `ExecutionMode` for *how* it runs and `OrderingStatus` for *whether the
  position on the canvas means anything*. No new visual grammar was needed; the
  dashed connector that v0.1 introduced for conditional calls already says it.
- **Three justifications, and no fourth.** Kotlin's `inline` rule (a language
  guarantee), Go's `go`/`defer` keywords, and a hand-written list of documented
  APIs. Everything else is `UNKNOWN`, said out loud.
- **`isAnonymousBody`**, which keeps a lambda out of the dispatch chooser and
  the saved-flow store. A lambda is analyzable as a frame but is not something a
  reader can name or store: its identity is a position in a file.

## 5. Defects found before the milestone closed

1. **A callback could not own the body it was supposed to show.** `FlowNode`
   required a frame-owning event to be a call, a constructor, or the entry, so
   the first end-to-end run threw `IllegalArgumentException` the moment a
   callback opened its child frame — and the run reported `FAILED` with the
   frame half-built. Every unit test passed, because extraction never builds a
   model.

   The fix is the invariant saying what it means: a callback owns a frame for
   the same reason a call does — there is a body to enter. What differs is when
   it runs, not whether it has one.

   The lesson is the one v0.4 kept teaching in a different costume: a model that
   is correct at one layer says nothing about the layer that consumes it. The
   acceptance suite exists to cross that boundary, and it is what caught this.

2. **A lambda became a dispatch candidate.** Making a lambda an analyzable
   declaration is what lets the run enter its body — but `DefinitionsScopedSearch`
   returns lambdas as implementations of a functional interface method, so the
   Choose Implementation dialog would have started offering entries named `{ }`
   whose stored key is a file offset that does not survive an edit.

   `isAnonymousBody` now separates the two questions: *can this be analyzed as a
   frame* and *is this something a reader can name and store*. Pins were already
   safe by construction — a pin is refused unless its key round-trips — which is
   worth recording as a guardrail that paid for itself.

3. **An immediately invoked Go closure was named by its whole source text.**
   `calleeNameOf` fell back to `expression.text`, so `func() { charge() }()`
   produced a card titled with the entire literal. It is `func()` now. This one
   predates v0.5 but only became visible when closures stopped being skipped.

4. **Java disagreed with the other two analyzers about a lambda's body.**
   `hasAnalyzableBody` still answered only for methods, so Java said a lambda has
   no body it can traverse while Kotlin and Go said it has. Nothing depended on
   it — the run does not consult it for callbacks — which is exactly why it would
   have sat there until something did.

5. **`enum.execution.UNKNOWN` read as "Unknown"**, which in a tooltip sitting
   next to a resolution status says nothing about *what* is unknown. It is
   "Timing not determined" / 「実行タイミング不明」 now — the point of the state is
   that the reader knows which question went unanswered.

6. **The first call in a frame never showed a project boundary** — found in the
   sandbox, and older than v0.5. The marker is drawn on the connector between
   two cards, and the first card has no predecessor, so `place()`'s two JDK calls
   were drawn differently: `Iterable.forEach()` was marked as crossing out of the
   project and `ExecutorService.submit()`, two cards above it, was not.

   The view model had it right all along — `boundaryBeforeCard` was already true
   for both — and the existing test asserted exactly that. Only the layout and
   the painting ignored it, which is the same shape as defect 2 in `V0.4_RESULTS.md`:
   a rule implemented everywhere except where the reader looks.

7. **A Go closure invoked in place produced two cards, one of them a failure.**
   Found in the sandbox. `go func() { charge() }()` drew an unresolved call card
   — `? ⚡ func()()`, dashed and red — directly above the callback card that had
   the body. There is no declaration to resolve here: the call and the body are
   the same thing, so the call card could only ever report itself as a dead end,
   and the doubled parentheses came from a short name that already ended in one.

   An invoked literal is now one event. A literal *handed* to a call still gets
   both, because there the call and the body really are two things.

8. **A gap left open on purpose**, recorded rather than quietly shipped: a
   method reference (`list.forEach(this::audit)`) and an anonymous class or
   object literal are still not callback events, so the same loop shows its body
   when written as a lambda and shows nothing when written as a reference
   (`KNOWN_LIMITATIONS.md` §45). The reason is scope, not difficulty.

## 6. Not verified here

- **Production IDE.** The ZIP has not been installed into a real IntelliJ IDEA
  Ultimate. That is v1.0's job (`PLAN.md` §17), and the sandbox plus the Verifier
  are what stand in for it until then.
- **Real projects.** Timing coverage was measured against the fixtures and the
  manual samples, not against a codebase that did not know it was being read.
  How often `UNKNOWN` appears in practice — and therefore whether the documented
  list is the right size — is an open question for the stabilization milestone.
- **The Japanese pass.** New strings were translated as they were added, but the
  full read-through of the Japanese bundle in context is v1.0 work.
