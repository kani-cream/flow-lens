# Flow Lens v0.1 Implementation Specification

## 1. Purpose

This document removes implementation ambiguity for v0.1.

`PLAN.md` defines product direction. This file defines the behavior that v0.1 code and tests should implement.

v0.1 proves one end-to-end interaction:

> In IntelliJ IDEA Ultimate, put the caret in a Java, Kotlin, or Go function/method, run Flow Lens, and receive a useful visual map of reachable explicit calls without blocking the IDE or pretending static uncertainty is certainty.

---

## 2. Supported Host and Languages

### Host IDE

v0.1 targets:

- **IntelliJ IDEA Ultimate**

The exact minimum compatible build is fixed during Milestone 0 and then treated as part of the release contract.

Go support requires a compatible JetBrains Go language plugin.

### Languages

v0.1 targets:

- Java
- Kotlin
- Go

All languages produce the same language-neutral model. Language-specific PSI/API objects must not leak into rendering, persistence, export, or shared navigation abstractions.

Analysis may cross Java/Kotlin language boundaries through an analyzer registry.

---

## 3. Analyzer Dispatch

Analyzer selection happens for each resolved callable, not only once for the root.

Conceptual contract:

```text
FlowLanguageAnalyzerRegistry
- findAnalyzer(element)

FlowLanguageAnalyzer
- supports(element)
- findContainingEntryPoint(caret)
- extractDirectFlow(callable)
- resolveCall(callSite)
```

Example:

```text
Java Controller
  ↓ resolve
Kotlin Service
  ↓ resolve
Java Repository
```

The next target is handed to the matching analyzer before its body is traversed.

---

## 4. Supported Entry Points

### Java

Supported:

- instance methods.
- static methods.
- constructors with an explicit analyzable body.

Not independent entry points in v0.1:

- static initializer blocks.
- instance initializer blocks.
- lambdas.
- abstract methods without a body.
- native methods.

### Kotlin

Supported:

- named top-level functions.
- named member functions.
- constructors with an explicit analyzable body.

Not independent entry points in v0.1:

- anonymous functions.
- lambdas.
- abstract functions without implementation.

### Go

Supported:

- package functions.
- methods with receivers.

Not independent entry points in v0.1:

- function literals / closures.

### Caret behavior

If the caret is inside a supported declaration or its signature, that containing declaration is the entry point.

Otherwise analysis does not start and the UI presents a concise message such as:

```text
Flow Lens could not find a supported function or method at the caret.
```

No fallback guessing is allowed.

---

## 5. Explicit-Call Coverage

v0.1 is an explicit callable-flow analyzer.

### Java

Recognize:

- normal method invocation.
- static method invocation.
- `new` constructor invocation.
- explicit `this(...)` constructor invocation.
- explicit `super(...)` constructor invocation.

Do not create call nodes for plain field reads/writes.

Implicit initializer/super-constructor sequencing is not reconstructed unless explicitly implemented and tested.

### Kotlin

Recognize:

- named function calls.
- member function calls.
- constructor calls.
- resolvable extension-function calls.

Do not automatically invent callable events for:

- property access syntax.
- delegated properties.
- default argument machinery.
- operator/desugared calls.
- generated bridge/synthetic behavior.

Such behavior may be added later only as explicit semantic support.

### Go

Recognize:

- package-level function calls.
- method calls.
- built-ins as terminal built-in operations when useful.

Do not model plain selector/field access as a call.

Preserve syntactic execution mode:

```text
go f()     → GOROUTINE
defer f()  → DEFERRED
```

v0.1 does not need full goroutine or defer lane visualization, but this information must survive in the shared model.

---

## 6. Evaluation and Ordering

Flow Lens must not use naive AST/PSI preorder as execution order.

### Nested calls

```java
save(convert(load(id)));
```

Expected:

```text
load(id)
convert(...)
save(...)
```

### Multiple arguments

Where language semantics define left-to-right evaluation, preserve it.

```java
foo(a(), b());
```

Expected:

```text
a()
b()
foo()
```

### Chained calls

```java
source().transform().save();
```

Expected:

```text
source()
transform()
save()
```

### Uncertain ordering

Every event/group may carry:

```text
DETERMINISTIC
APPROXIMATE
UNSPECIFIED
```

If Flow Lens cannot justify a total order, the renderer must not show an ordinary certain sequential connector merely because it is visually convenient.

### Go defer

For:

```go
defer f(a())
```

argument-expression events such as `a()` are placed according to Go evaluation semantics, while the deferred invocation of `f` itself is represented with `executionMode = DEFERRED` rather than as an ordinary immediate synchronous continuation.

## 7. Shared Model Semantics

### Analysis result

```text
FlowAnalysisResult
- status
- rootFrame
- nodeCount
- controlFlowIncomplete
- sourceRevision
- diagnostics
```

Status:

```text
RUNNING
COMPLETED
TRUNCATED
CANCELLED
STALE
FAILED
```

### Flow frame

A `FlowFrame` represents one analyzed callable body.

```text
FlowFrame
- symbol
- entryLocation
- depth
- events[]
```

### Flow node

A `FlowNode` represents one semantic event/call site, not the globally unique target method.

```text
FlowNode
- id
- kind
- callSiteLocation
- targetSymbol?
- targetFrame?
- depth
- resolutionStatus
- dispatchConfidence
- executionMode
- orderingStatus
- metadata
```

Two calls to the same target from different call sites remain two separate nodes.

### Node kind

```text
ENTRY
CALL
CONSTRUCTOR
CONDITION
SWITCH
LOOP
RETURN
THROW
TRY
CATCH
FINALLY
CYCLE
LIMIT
STATUS
```

### Resolution status

```text
PROJECT_LOCAL
EXTERNAL
UNRESOLVED
BUILT_IN
```

### Dispatch confidence

```text
EXACT
DECLARED_TARGET
AMBIGUOUS
UNKNOWN
```

### Execution mode

```text
SYNC
ASYNC
GOROUTINE
DEFERRED
UNKNOWN
```

### Ordering status

```text
DETERMINISTIC
APPROXIMATE
UNSPECIFIED
```

These dimensions are deliberately separate. Do not introduce redundant types such as both `EXTERNAL_CALL` and `resolutionStatus = EXTERNAL`.

## 8. Resolution and Dispatch Rules

### Exact

Use `EXACT` when one target is statically justified for the modeled semantics, such as resolvable static/private/final/non-overridable calls, constructors, explicit superclass dispatch, Kotlin top-level functions, or Go package functions.

### Declared target

For a normal virtual call where IntelliJ resolves a concrete declared implementation body but runtime overriding remains possible:

```text
resolutionStatus = PROJECT_LOCAL
dispatchConfidence = DECLARED_TARGET
```

Flow Lens may recursively analyze that declared body.

The UI must indicate that runtime override is possible; it must not present this as guaranteed dispatch.

### Ambiguous

Use `AMBIGUOUS` when no single target body can responsibly be selected as the continuation, for example an interface/abstract contract with multiple plausible implementations and no concrete body appropriate to follow.

v0.1 stops recursive traversal at this node.

### Unresolved

If no reliable target can be found:

- retain the call-site event.
- set `resolutionStatus = UNRESOLVED`.
- do not recurse.
- continue analyzing unrelated events.

One failure must not fail the entire analysis.

### External

Dependency, JDK/runtime, SDK, or otherwise non-project source is terminal by default.

External source navigation may still be offered when IntelliJ can navigate there.

---

## 9. Recursive Depth

Depth counts only entry into another callable body.

```text
root frame                     D0
direct project-local callee    D1
callee of that method          D2
```

Conditions, loops, visual containers, external nodes, unresolved nodes, and limit markers do not consume method depth.

Default:

```text
Max depth = 3
```

Attempting to cross beyond the limit produces a visible `LIMIT` event and does not enter the target frame.

---

## 10. Node Limit

Default:

```text
Max persistent semantic nodes = 100
```

Counting rules:

- persistent semantic model nodes count.
- temporary renderer-only `resolving…` placeholders do not count.
- the final reserved semantic slot may be consumed by a `LIMIT` node.

When exhausted:

1. stop producing further ordinary semantic nodes.
2. expose a visible `LIMIT` marker.
3. mark result `TRUNCATED`.
4. preserve all completed nodes for navigation.

The limit is enforced during traversal.

---

## 11. Project and Test Boundaries

### Project-local

Project source content is eligible for recursive analysis.

### Tests

Tests are excluded from recursive traversal by default.

If a user explicitly starts analysis from a test entry point, the root may be analyzed, but traversal into additional test-only code obeys `Include tests`.

### External

External calls are terminal by default.

The renderer represents the project crossing locally on the call path; it does not require a canvas-wide boundary line.

---

## 12. Cycles and Recursion

Cycle detection is based on the current callable traversal path.

```text
A.run
  ↓
B.work
  ↓
A.run
  ↓
CYCLE → A.run
```

The same symbol may appear again in another call site or independent branch/path.

Do not globally deduplicate symbols from the visual map.

---

## 13. Control Flow in v0.1

Full branch/loop semantics belong to v0.2.

v0.1 must not pretend flattened calls prove a single unconditional runtime path.

Rules:

1. Calls inside `if`, `switch/when`, Go `switch`, loops, and similar structures may be discovered.
2. v0.1 may show conservative structural/evaluation order without constructing a full branch graph.
3. The result sets `controlFlowIncomplete = true` when complete path semantics are not represented.
4. Flow Canvas visibly shows `Control flow simplified`.
5. Ordinary certain connectors must not imply a path guarantee the analyzer has not established.

---

## 14. Progressive Traversal

The user-visible traversal policy is local-first / breadth-first-biased.

Preferred progression:

```text
1. Extract root frame direct events.
2. Render the complete root-level picture.
3. Resolve/analyze depth-1 project-local targets.
4. Make child frames available.
5. Continue deeper within limits.
```

Do not deeply expand the first root call while later direct root calls have not yet appeared unless implementation constraints require it.

This rule is primarily an UX/layout-stability contract.

---

## 15. Indexing and Source Mutation

### Indexing

If required IntelliJ indexes are unavailable, Flow Lens waits instead of generating misleading unresolved results.

Visible state:

```text
Waiting for IntelliJ indexes…
```

### Source changes

If relevant source changes during analysis and the current result can no longer be trusted:

- stop/cancel affected traversal cooperatively.
- mark result `STALE`.
- retain safe partial nodes for inspection.
- expose re-analysis.

Do not silently combine events extracted from incompatible PSI/source revisions.

---

## 16. Active Analysis and Cancellation

Only one analysis may run per project in v0.1.

Starting another analysis:

1. cancels the previous run.
2. replaces Current Flow with the new root.
3. starts progressive analysis/rendering.

Cancellation:

- is cooperative.
- retains completed nodes.
- marks result `CANCELLED`.
- leaves completed source navigation working.

Meaningful traversal/resolution must not run on the EDT.

---

## 17. Flow Canvas Initial State

v0.1 must not fall back to plain `JTree` as the final product experience.

Initial visual expansion:

- root frame: expanded.
- direct root call cards: visible.
- child target frames: collapsed.
- analyzed deeper content may exist in memory but is opened only on user expansion.

This prevents 100 analyzed nodes from appearing as one huge wall.

Minimum canvas behavior:

- top-to-bottom primary direction.
- distinct root card.
- compact call/function cards.
- distinct external, unresolved, ambiguous, declared-target, cycle, and limit states.
- nested target-frame expansion.
- progressive appearance while analysis runs.
- selection + details area.
- pan/scroll and fit-to-view.
- source navigation.

Detailed rules live in `VISUAL_DESIGN.md`.

## 18. Source Navigation

A call event may have two valid destinations:

### Open Target

Navigate to the resolved target declaration.

Default for resolved call cards:

- double click.
- Enter.

### Open Call Site

Navigate to the invocation that created this specific event.

Available as a context action/details action.

### Unresolved

Because no target is known, default navigation opens the call site.

### Entry

Entry card opens the entry declaration.

## 19. Settings

Defaults:

```text
Max depth             3
Max semantic nodes  100
Include tests       OFF
Include libraries   OFF
```

Settings are project-scoped.

Current Flow does not need to survive IDE restart.

---

## 20. Error Handling

- One call-resolution failure does not abort the full analysis.
- unexpected analyzer exceptions are logged and surfaced as concise non-destructive diagnostics.
- partial safe results remain usable.
- unsupported constructs never crash the IDE.
- invalidated PSI/source state results in stale/cancel behavior rather than continued unsafe traversal.

## 21. Acceptance Cases

### A — Linear calls

```java
void run() {
    a();
    b();
    c();
}
```

Expected direct event order: `a`, `b`, `c`.

### B — Nested calls

```java
save(convert(load()));
```

Expected: `load`, `convert`, `save`.

### C — Chained calls

```java
source().transform().save();
```

Expected: `source`, `transform`, `save`.

### D — Duplicate target

```java
validate(a);
validate(b);
```

Expected: two call-site nodes sharing the same target symbol.

### E — Mixed Java/Kotlin

Java root resolves a Kotlin method, which resolves a Java method.

Expected: analyzer registry switches analyzers while producing one continuous shared model.

### F — Exact dispatch

Static/private/final or equivalent exact target.

Expected: `dispatchConfidence = EXACT`; body may be recursively analyzed.

### G — Declared target

Concrete virtual method body exists but runtime override is possible.

Expected: `dispatchConfidence = DECLARED_TARGET`; declared body may be analyzed; UI indicates runtime override possibility.

### H — Ambiguous dispatch

Interface/abstract target has no responsible single continuation.

Expected: `dispatchConfidence = AMBIGUOUS`; traversal stops at call.

### I — Unresolved call

Expected: unresolved event; unrelated events continue.

### J — External call

Expected: terminal external event and local project-boundary treatment.

### K — Cycle

Expected: cycle marker, no infinite recursion.

### L — Depth limit

Expected: visible limit marker at attempted expansion beyond configured depth.

### M — Node limit

Expected: at most configured semantic-node budget including truncation marker; result is usable and `TRUNCATED`.

### N — Cancel

Expected: partial map remains navigable and result becomes `CANCELLED`.

### O — Indexing

Expected: wait state rather than mass unresolved output.

### P — Source edit during analysis

Expected: affected result becomes `STALE` rather than mixing revisions.

### Q — Go goroutine

```go
go notify()
```

Expected: call event preserves `executionMode = GOROUTINE`.

### R — Go defer

```go
defer cleanup()
```

Expected: call event preserves `executionMode = DEFERRED` and is not presented as an ordinary immediate call.

### S — Control flow present

Expected: calls may be discovered but `controlFlowIncomplete = true`, with visible simplified-control-flow disclosure.

### T — Initial canvas expansion

Expected: root frame expanded; child frames collapsed by default.

---

## 22. Definition of Done for v0.1

v0.1 is complete when:

1. IntelliJ IDEA Ultimate is the verified host environment.
2. Java, Kotlin, and Go each support a reliable basic explicit-call flow.
3. Java/Kotlin mixed-language traversal works for supported call cases.
4. Nested/chained calls are not rendered in naive AST preorder.
5. Call-site identity and target-symbol identity are distinct.
6. `FlowFrame` supports inline nested expansion without duplicating semantic identity.
7. dispatch is classified as exact, declared-target, ambiguous, or unknown where applicable.
8. project-local recursion respects depth and cycle rules.
9. external, unresolved, ambiguous, declared-target, cycle, and limit states are visually distinguishable.
10. Go goroutine/defer semantics are retained as metadata.
11. indexing is not misreported as unresolved code.
12. source mutation cannot silently corrupt an in-progress result.
13. analysis is cancellable and does not perform meaningful work on the EDT.
14. Flow Canvas progressively renders local-first and is materially more informative than a call tree.
15. root frame is initially expanded while child frames are collapsed.
16. users can navigate separately to target declaration and call site where available.
17. simplified v0.1 control-flow treatment is explicitly disclosed.
18. fixture-based tests cover the core cases above for Java, Kotlin, and Go.
