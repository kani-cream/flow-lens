# Flow Lens v0.1 Implementation Specification

## 1. Purpose

This document removes implementation ambiguity for v0.1.

`PLAN.md` defines product direction. This file defines the behavior that v0.1 code and tests should implement.

v0.1 proves one end-to-end interaction:

> Put the caret in a Java, Kotlin, or Go method/function, run Flow Lens, and receive a useful visual map of the reachable project-local calls without blocking the IDE or pretending static uncertainty is certainty.

---

## 2. Supported Languages

v0.1 targets:

- Java
- Kotlin
- Go

All three languages must produce the same language-neutral `FlowAnalysisResult` model.

Language-specific PSI/API objects must not leak into the renderer.

---

## 3. Supported Entry Points

### Java

Supported:

- Instance methods.
- Static methods.
- Constructors.

Not supported as independent entry points in v0.1:

- Static initializer blocks.
- Instance initializer blocks.
- Lambdas.
- Abstract methods without a body.
- Native methods.

### Kotlin

Supported:

- Named top-level functions.
- Named member functions.
- Constructors where a usable body/initialization flow can be resolved by the analyzer.

Not supported as independent entry points in v0.1:

- Anonymous functions.
- Lambdas.
- Abstract functions without implementation.

### Go

Supported:

- Package functions.
- Methods with receivers.

Not supported as independent entry points in v0.1:

- Function literals / closures.

Function literals may appear as call arguments or values but are not recursively treated as normal named entry points in v0.1.

### Caret behavior

If the caret is inside a supported declaration or its signature, Flow Lens analyzes that containing declaration.

If no supported entry point can be found, analysis does not start and the UI presents a non-destructive message such as:

```text
Flow Lens could not find a supported method/function at the caret.
```

No fallback guessing is allowed.

---

## 4. Calls Recognized in v0.1

### Java

Recognize:

- Normal method invocation.
- Static method invocation.
- Constructor invocation using `new`.
- Explicit `this(...)` constructor invocation.
- Explicit `super(...)` constructor invocation.

Do not create call nodes for plain field reads/writes.

### Kotlin

Recognize:

- Named function calls.
- Member function calls.
- Constructor calls.
- Extension-function calls where resolvable.

Property access is not automatically treated as a function call in the shared model unless the analyzer can reliably identify an actual callable accessor and the behavior is explicitly implemented and tested. v0.1 may leave property access out rather than inconsistently inventing calls.

### Go

Recognize:

- Package-level function calls.
- Method calls.
- Built-in calls may be represented as terminal/built-in operations if needed, but they are not recursively analyzed as project functions.

Do not model ordinary field/selector access as a call.

`go f()` is recognized as containing a call, but v0.1 is not required to model goroutine concurrency semantics. The result must be marked so later versions can introduce an `ASYNC_BOUNDARY` without changing the call-site identity model.

---

## 5. Evaluation Order

Flow Lens must not use a naive AST/PSI preorder as execution order.

The analyzer should emit call events in the order in which the language semantics require those calls to be evaluated.

### Nested calls

Example:

```java
save(convert(load(id)));
```

Expected event order:

```text
load(id)
convert(...)
save(...)
```

### Multiple argument calls

For languages/cases where left-to-right call evaluation is defined, preserve it.

Example:

```java
foo(a(), b());
```

Expected:

```text
a()
b()
foo()
```

### Chained calls

Example:

```java
a().b().c();
```

Expected conceptual order:

```text
a()
b()
c()
```

Each call site is a separate node.

### Unspecified/uncertain ordering

If the language semantics or available PSI representation do not justify a deterministic order, Flow Lens must not invent one merely to make the diagram linear.

The analysis model should allow an ordering-confidence/status marker such as:

```text
DETERMINISTIC
APPROXIMATE
UNSPECIFIED
```

v0.1 UI may use a compact warning/badge for non-deterministic or approximate ordering.

---

## 6. Call Site Identity

A `FlowNode` represents a call-site event.

It is not equivalent to the target method/function declaration.

Required conceptual fields:

```text
FlowNode
- id
- type
- callSiteLocation
- targetSymbol
- displayName
- depth
- resolutionStatus
- orderingStatus
```

Two calls to the same target from different source offsets produce two different nodes.

Example:

```java
validate(user);
save(user);
validate(order);
```

Expected nodes:

```text
validate(user)
save(user)
validate(order)
```

The two `validate` nodes may share the same `targetSymbol` but must remain separate events.

---

## 7. Recursive Depth

Depth counts only crossings into another resolved function/method body.

Entry point:

```text
Depth 0
```

A directly called project-local method:

```text
Depth 1
```

A method called by that method:

```text
Depth 2
```

Conditions, loops, visual containers, external markers, unresolved markers, and limit markers do not consume method depth.

Default maximum depth:

```text
3
```

When recursion would exceed the limit, create a visible `LIMIT_REACHED` terminal child and do not enter the target body.

---

## 8. Node Limit

Default maximum total nodes:

```text
100
```

Once the node budget is exhausted:

1. Stop creating further normal nodes.
2. Add a visible `LIMIT_REACHED` marker when possible without violating internal safety.
3. Mark the analysis result as truncated.
4. Keep all already-produced nodes usable.

The limit must be enforced during traversal, not after complete graph construction.

---

## 9. Project, External, and Built-in Boundaries

### Project-local

A target that belongs to project source content is eligible for recursive analysis.

### Tests

Tests are excluded from recursive analysis by default.

If the entry point itself is explicitly selected in test source, analysis may analyze the selected entry point, but traversal into other test-only code should obey the `Include tests` setting.

### External

Targets in dependencies, SDK/JDK/runtime libraries, or other non-project source are terminal by default.

Expected conceptual result:

```text
projectCall()
   ↓
PROJECT BOUNDARY
   ↓
external.Library.call()
```

The external node should display the resolved target name when available.

### Built-ins

Language built-ins may be displayed distinctly from project-local calls but must not trigger recursive project traversal unless they resolve to actual project declarations.

---

## 10. Resolution Status

Every callable event has a resolution status.

Suggested values:

```text
PROJECT_LOCAL
EXTERNAL
AMBIGUOUS
UNRESOLVED
BUILT_IN
```

### Ambiguous

If more than one runtime target is statically plausible and v0.1 cannot justify one unique target, create an `AMBIGUOUS_CALL` and stop traversal at that call.

v0.1 does **not** automatically pick the declaration type's method implementation merely because it is easy to resolve syntactically.

Candidate discovery/selection UI is a later milestone.

### Unresolved

If no reliable target can be found:

- Create `UNRESOLVED_CALL`.
- Retain the call-site source location.
- Do not recursively traverse it.
- Continue analyzing unrelated calls.

One failed resolution must not fail the full analysis.

---

## 11. Cycles and Recursion

Cycle detection is based on the current recursive traversal path.

Example:

```text
A.foo()
  ↓
B.bar()
  ↓
A.foo()
  ↓
CYCLE → A.foo()
```

The cycle node references the previously visited symbol/callable in the current path.

The same method/function is allowed to appear again in another branch, another call site, or another independent traversal path.

Do not globally deduplicate methods from the visual map.

---

## 12. Control-Flow Constructs in v0.1

Full branch/loop semantics belong to v0.2.

However, v0.1 must not imply that it has proven a single unconditional runtime path when the selected method contains unsupported control-flow structure.

Rules:

1. Calls inside `if`, `switch/when`, loops, and similar structures may still be discovered.
2. v0.1 may present them in conservative structural/source order rather than a complete branch graph.
3. The analysis result must carry a `controlFlowIncomplete` or equivalent flag when complete path semantics are not represented.
4. Flow Canvas must surface a compact indication such as `Control flow simplified` when this flag is present.
5. v0.2 replaces this simplified treatment with explicit conditions, branches, merges, and loop containers.

This rule prevents v0.1 from presenting flattened branch calls as a guaranteed runtime sequence without warning.

---

## 13. Concurrency in v0.1

v0.1 does not promise full concurrent-flow analysis.

### Java / Kotlin

Executor, future, coroutine, callback, and similar async semantics may remain ordinary/unknown call structures unless a safe marker is trivial to produce.

### Go

The analyzer should identify that a call is syntactically launched with `go` and preserve this fact as metadata. It is acceptable for v0.1 rendering to use a simple async badge instead of a full parallel lane.

A later version will promote these markers into first-class `ASYNC_BOUNDARY` visualization.

---

## 14. Active Analysis and Cancellation

Only one analysis may run per project in v0.1.

When a new analysis starts:

1. Cancel the previous analysis.
2. Reset/replace Current Flow for the new entry point.
3. Begin progressive rendering of the new result.

Cancellation behavior:

- Analysis stops cooperatively.
- Already-built nodes remain visible.
- Result is marked `CANCELLED` / partial.
- Source navigation for completed nodes continues to work.

The EDT must never be blocked by meaningful traversal or resolution work.

---

## 15. v0.1 Flow Canvas Behavior

v0.1 is not allowed to fall back to a plain `JTree` as the final product experience.

Minimum visual behavior:

- Top-to-bottom default reading direction.
- Distinct entry card.
- Distinct method/function call cards.
- Distinct external, unresolved, ambiguous, cycle, and limit states.
- Connectors with enough routing/spacing to read paths clearly.
- Progressive insertion of nodes while analysis runs.
- Selected-node emphasis.
- Source navigation by double click / Enter.
- Details shown on selection without permanently bloating every card.
- Pan/scroll and fit-to-view behavior sufficient for the v0.1 layout.

Detailed rules live in `VISUAL_DESIGN.md`.

---

## 16. Settings

v0.1 defaults:

```text
Max depth              3
Max total nodes      100
Include tests        OFF
Include libraries    OFF
```

Settings are project-scoped in v0.1.

Current Flow is not required to survive IDE restart.

---

## 17. Error Handling

Analyzer failures should be isolated whenever possible.

Rules:

- A failure resolving one call does not abort the full analysis.
- Unexpected analyzer exceptions are reported in plugin logging and surfaced as a concise non-destructive UI error.
- Partial results remain usable when safe.
- No unsupported language construct should crash the IDE.

---

## 18. Acceptance Cases

The following cases should become automated or fixture-based tests where practical.

### Case A — Linear calls

```java
void run() {
    a();
    b();
    c();
}
```

Expected:

```text
run
 ├ a
 ├ b
 └ c
```

Visual order is `a`, then `b`, then `c`.

### Case B — Nested calls

```java
void run() {
    save(convert(load()));
}
```

Expected event order:

```text
load
convert
save
```

### Case C — Chained calls

```java
void run() {
    source().transform().save();
}
```

Expected event order:

```text
source
transform
save
```

### Case D — Duplicate target

```java
void run() {
    validate(a);
    validate(b);
}
```

Expected: two separate call-site nodes pointing to the same target symbol.

### Case E — Project recursion

```text
A.run → B.work → C.save
```

Expected: recurse while depth allows.

### Case F — Cycle

```text
A.run → B.work → A.run
```

Expected: terminal cycle marker instead of infinite recursion.

### Case G — External call

Expected: external terminal node, no library-body recursion by default.

### Case H — Unresolved call

Expected: unresolved terminal node; other calls continue to analyze.

### Case I — Ambiguous call

Expected: ambiguous terminal node; v0.1 does not silently select an implementation.

### Case J — Depth limit

Expected: visible limit marker at the attempted expansion beyond configured method depth.

### Case K — Node limit

Expected: partial usable result with visible truncated state.

### Case L — Cancel

Expected: analysis stops and already-rendered nodes remain navigable.

### Case M — Control flow present

Method contains branch/loop constructs.

Expected: v0.1 may simplify their internal call ordering, but result clearly indicates that control-flow semantics are simplified/incomplete.

### Case N — Java / Kotlin / Go parity

Equivalent simple call chains in all three languages produce equivalent shared model shapes and equivalent Flow Canvas semantics.

---

## 19. Definition of Done for v0.1

v0.1 is complete when:

1. Java, Kotlin, and Go each support a reliable basic function/method call-flow path.
2. Nested and chained calls are not rendered in naive AST preorder.
3. Calls are represented per call site.
4. Project-local recursion respects depth and cycle rules.
5. External, ambiguous, unresolved, and limit states are visually distinct.
6. Analysis is cancellable and never performs substantial work on the EDT.
7. The Flow Canvas progressively displays results and is visually more informative than a plain call tree.
8. Every source-backed completed node can navigate back to source.
9. Simplified v0.1 control-flow treatment is explicitly disclosed in the UI.
10. Core acceptance fixtures exist for Java, Kotlin, and Go.
