# v1.1 — Hiding external calls

Fixed semantics for an opt-in the owner requested on 2026-08-24: a setting that
removes calls to code outside the project from the map entirely, so a complex
flow can be read as the reader's own functions only.

---

## 1. Relation to the v1.0 decision

`V1.0_GROUPING_SPEC.md` §2 rejected "hide external calls" **as the default**,
and that reasoning stands: in `Login()`, ten external calls *are* the story, and
a map that silently dropped `CompareHashAndPassword` would lie about what the
function does. Grouping remains the default presentation.

What v1.1 adds is a choice, off by default. A reader who says "show me my own
code" is not being protected from a bad default — they are stating what they
want to read, and the map discloses what it removed (§5) so the omission is
never silent.

## 2. The setting

`Hide calls to code outside the project` — a project-level checkbox next to the
existing traversal options, persisted in `flowLens.xml`, snapshotted into
`FlowLimits` at run start like every other option (guardrails §8). Saved flows
and recents carry it, as they carry the other limits (`V0.3_SPEC.md` §5).

## 3. What hides

A call is hidden when **all** of the following hold:

1. the setting is on for the run;
2. it resolves as `EXTERNAL` or `BUILT_IN` — the same statuses grouping treats
   as outside the project (`V1.0_GROUPING_SPEC.md` §3);
3. it was not entered — no body of it is on the map (with
   `includeLibraries` on, an entered library call stays: following it was the
   point);
4. it was not handed a callback that is attached to it. `list.forEach { … }`
   keeps its card: the lambda is the reader's own code, the model attaches a
   body to its call by adjacency (`V0.5_SPEC.md` §5.5), and removing the call
   would hang the body on the wrong owner.

`UNRESOLVED` calls always stay: not knowing what a call is, is a finding, not
noise. `PROJECT_LOCAL` dead ends stay for the reason grouping never touched
them — they are the reader's own.

## 4. Where it happens

At append time in the run, before grouping, per sequence (a frame's events, one
branch's events). Hiding before grouping means a hidden run leaves no
`EXTERNAL_GROUP` behind, and — the reason this is an analysis-time rule rather
than a view filter — hidden calls cost no node budget, which goes instead to
the project code the reader asked to see. The first real project spent 90 of
100 nodes on external calls (`V1.0_GROUPING_SPEC.md` §1); with hiding on, that
budget reaches the handlers.

## 5. Disclosure

Hidden calls leave no node, so the count rides on the result
(`FlowAnalysisResult.hiddenExternalCount`) and surfaces everywhere the map
explains itself: the status area's stop reasons and both exports, as
`Hidden by settings — outside the project: N`. The reason has no node to
select, so unlike the other reasons it is a disclosure, not an entry point.

A map with calls removed must say so. Absence would read as "nothing was
called", and that is the one thing this feature must never claim.

## 6. Known edges

- A kept call (one that owns a callback) can still join a library group when
  three groupable calls happen to be adjacent; grouping already behaved this
  way before v1.1 and is unchanged.
- The running counters count what is appended, so `external` in the status line
  reflects visible external calls; the hidden count is its own line.
