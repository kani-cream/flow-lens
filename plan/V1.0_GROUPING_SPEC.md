# v1.0 — Library call grouping

Fixed semantics for the one capability v1.0 adds. Scoped by the owner on
2026-08-19 after the first real-project run, with the reason stated plainly:
**わかりづらいものは使いたくない.**

---

## 1. What the run showed

Two entry points in a real Go service (`stock-oracle`), both analyzed at the
default limits:

| Entry point | Nodes | External | The reader's own code |
|---|---|---|---|
| `router.New()` | 100 (truncated) | **90** | 10 |
| `AuthHandler.Login()` | 100 (truncated) | 41 | 59 |

`New()` registers 76 routes. The map drew 76 `RouterGroup.GET()` /`POST()` cards,
spent the whole node budget on calls it never entered, and showed none of the 73
handler functions the reader actually wanted. It was truthful and useless.

## 2. Why "hide external calls" is the wrong fix

The obvious reading of §1 is that library calls do not belong on the map. That
reading breaks the other entry point.

In `Login()`, ten of the forty external calls *are* the story:

```text
ShouldBindJSON → QueryRowContext / Scan → CompareHashAndPassword
  → NewWithClaims / SignedString → SetCookie → JSON
```

Remove them and what the function does is gone. The other thirty are plumbing —
`len`, `append`, `Index`, `TrimSpace`, `Errorf`, `NewNumericDate` ×3.

`ShouldBindJSON` and `len` are both external, both not followed, and one is
essential while the other is noise. **External is not the discriminator.**

What separates the two maps is *repetition*: `RouterGroup.GET()` forty-seven
times says nothing the first one did not, while ten different library calls in a
row each say something. So the rule collapses runs, not libraries.

---

## 3. What collapses

A **library group** replaces a run of consecutive events in one sequence when
all of the following hold:

1. every member is a `CALL` or `CONSTRUCTOR`;
2. no member was entered — none has a body on the map;
3. every member resolves as `EXTERNAL` or `BUILT_IN`;
4. every member shares the same container name — the Go package, the Java or
   Kotlin declaring type;
5. there are at least **three** of them.

"Consecutive" means adjacent in the same sequence: a frame's events, or one
branch's events. A group never spans a structure boundary, and never spans a
branch.

### 3.1 What never collapses

- A call whose body is on the map. Following it is the point.
- A project-local call, even a dead end. That is the reader's own code.
- A structure, a terminator, a callback, a cycle, a limit marker.
- A run of two. Two cards are not yet noise, and a group of two costs a concept
  to save a line.

### 3.2 Why the container, not the package root

`gin`, `strings`, `jwt` are what the reader recognizes. Grouping by anything
coarser — "all external" — merges `bcrypt.CompareHashAndPassword` into the run
beside it and loses §2's ten. Grouping by anything finer — the exact callee —
leaves `RouterGroup.GET` and `RouterGroup.POST` as separate groups, which is
most of the noise back again.

---

## 4. What a group is in the model

`FlowNodeKind.EXTERNAL_GROUP`, holding its members in a single
`BranchKind.GROUP` branch.

A group is **not** a structure. Its members are one run of steps drawn as one
card, in source order; a structure's branches are alternatives. The distinction
matters because `isConditional` is false for a group — every member runs — while
a `CASE` may not.

Grouping happens **once, where the model is built**, not in each renderer. The
canvas, the Markdown export and the Mermaid export all receive a model that
already has the groups in it. v0.5 hardening cost a milestone by letting two
renderers each decide the same question; this does not repeat it.

### 4.1 The node budget

**A group claims one node. Its members claim none.**

That is the half of the fix that matters as much as the noise: `New()` truncated
at 100 nodes of which 90 were unenterable, so the budget was exhausted before
the analysis reached anything worth reading. A group of 47 costing 1 gives the
budget back to the code the reader came for.

The members are still produced, resolved and classified — the work is the same.
What changes is what the budget is spent on, which is model and screen size.

## 5. What the reader sees

```text
Login()
  ShouldBindJSON()          gin        a single call still stands alone
  ▸ strings — 5 calls       external   a run, collapsed, openable
  CompareHashAndPassword()  bcrypt
  ▸ jwt — 5 calls           external
  SetCookie()               gin
```

Requirements:

1. The card names the **container and the count**: `gin — 47 calls`. A number a
   reader cannot act on is a report; this one opens.
2. **Collapsed by default, expandable**, like an analyzed body. Expanding shows
   the members in source order, each the card it would have been.
3. It reads as a boundary, not as a step of the reader's own code — the group
   carries `EXTERNAL` resolution, and the project-boundary marker still applies.
4. The "not followed" summary counts **members**, not groups. Forty-seven calls
   left the project whether or not they were drawn on forty-seven cards.
5. Both exports disclose the count; **Markdown also lists the members**, nested
   under the group. Mermaid draws the group as a single node and does not draw
   the members: putting forty-seven boxes back into a diagram would defeat the
   rule there exactly as it does on the canvas, and the count is what keeps it
   honest. An export that silently dropped forty-seven calls with no number
   would be the dishonesty this whole rule exists to avoid.

---

## 6. Disclosure

Grouping hides nothing: every member is in the model, in the exports, and one
click away on the canvas. What it removes is repetition.

That claim has to survive the obvious objection — *the reader no longer sees
that `GET` was called forty-seven times*. They do: the count says so, and it is
the first thing on the card.

## 7. Acceptance cases

| # | Case | Expected |
|---|---|---|
| A | Three consecutive `gin` calls, none entered | one group, count 3, members in order |
| B | Two consecutive `gin` calls | no group; both cards stay |
| C | `gin`, `strings`, `gin` consecutive | no group; the container changes each time |
| D | `gin` ×3, a project call, `gin` ×3 | two groups; the project call separates them |
| E | An external call whose body was entered (`Include libraries` on) | never grouped |
| F | A run split across a branch boundary | grouped within each branch only |
| G | A group inside a `then` branch | grouped, and still not conditional in itself |
| H | 47 members | one node against the budget, not 47 |
| I | A run that would exhaust the budget | the group is one node; the run does not truncate the map |
| J | The "not followed" count with a group of 47 | still says 47 |
| K | Markdown export | the group, its count, and its members |
| L | Mermaid export | the group as one node; the sequence passes through it |
| M | Details panel on a group | container, count, resolution — no dispatch, no depth claim |
| N | `router.New()` from the real project | the reader's own code is reachable within the default budget |

## 8. Known limitations this introduces

To be recorded in `KNOWN_LIMITATIONS.md`:

1. Grouping is by adjacency. The same library called in three places separated
   by project code makes three groups, not one — because the map is a sequence,
   and merging them would move calls in time.
2. The threshold of three is a judgement, not a measurement.
3. A container name is not a library. Two Java classes from one dependency group
   separately; two Go packages of one module do too.
