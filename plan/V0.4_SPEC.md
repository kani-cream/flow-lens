# Flow Lens v0.4 Implementation Specification

## 1. Purpose

Two gaps close here.

An ambiguous call is a dead end today. `Gateway.charge()` resolves to an
interface method, no single continuation can be proven, and the map stops — even
when the project contains exactly one implementation and the developer knows
which one runs. v0.4 shows the candidates and lets the reader pick one, without
ever letting a picked path look like a proven one.

And a flow cannot leave the IDE. v0.4 exports it as Markdown and as a Mermaid
flowchart, carrying the same uncertainty the canvas shows, so a map can go into
a review, an issue, or a design document.

`PLAN.md` §17 defines the scope. This document fixes the semantics and the
observable behavior, the way `V0.3_SPEC.md` did for v0.3.

---

## 2. Scope

### In scope

| Feature | What it is |
|---|---|
| Candidate discovery | For a call that cannot be resolved to one implementation, the implementations the project actually contains. |
| Dispatch choice | "When you would stop at this callable, continue into that one." Applies to the run, is visible, and is removable. |
| Markdown export | The flow as a document, uncertainty included. |
| Mermaid flowchart export | The flow as a diagram that renders in GitHub Markdown. |

### Out of scope, deliberately

- **Mermaid sequence export** and **copy structured context for external tools**,
  both listed in `PLAN.md` §17. The owner deferred them on 2026-08-18: a
  sequence diagram implies participants exchanging ordered messages, which a
  branching flow is not, and the structured-context format is worth designing
  against a real consumer rather than in advance. Recorded here rather than
  silently dropped; they return in a later milestone if wanted.
- **Persisting dispatch choices.** A choice lives for the session. Saved Flows
  store an entry point and limits (`V0.3_SPEC.md` §5); adding choices to them is
  a separate decision.
- **Inferring the likely implementation.** Flow Lens does not rank candidates by
  dependency injection configuration, naming, or usage frequency. It lists what
  exists; the reader chooses.
- **Exporting anything not on the map.** An export is a rendering of the current
  result, never a second analysis with different rules.

## 3. Candidates

A call has candidates when it resolves to a declaration that could be overridden
or implemented — an interface method, an abstract method, an `open` Kotlin
function, a Go interface method — which is exactly the set the model already
marks `AMBIGUOUS` or `DECLARED_TARGET`.

Rules:

1. **Discovery is on demand.** Candidates are searched when the reader asks for
   them, not during analysis. Searching every ambiguous call while analyzing
   would cost an inheritance search per node and change the cost of a run.
2. **The search is language-neutral.** `DefinitionsScopedSearch` is what the IDE
   itself uses for Go to Implementation, so Java, Kotlin, and Go are covered
   without a per-language code path, and a language the plugin gains later is
   covered too.
3. **Only analyzable candidates are offered.** An implementation in a library or
   without a body cannot be followed, so it is not presented as a choice.
4. **The list is bounded and says so.** At most 20 candidates; if the search
   found more, the list reports that it is showing part of them. A silently
   truncated list of implementations would be worse than no list.
5. **The order is deterministic** — by container name, then by display name — so
   the same call always presents the same list.
6. **Nothing is chosen automatically.** A single candidate is still a choice the
   reader makes. Flow Lens does not decide that one implementation means one
   runtime target: a framework can substitute another at runtime, which is
   exactly the uncertainty the marker exists for.

## 4. Dispatch choices

A choice says: *when the traversal would stop at callable A because it cannot
prove a continuation, continue into callable B instead.*

Rules:

1. **A choice is keyed by callable, not by call site.** Choosing
   `Gateway.charge() → StripeGateway.charge()` applies to every call to
   `Gateway.charge()` in the flow. This matches how the decision is actually
   made — "in this codebase, that interface is that class" — and it survives
   re-analysis, where a call site's identity would not. §9 records the
   consequence: two call sites of one interface method cannot be given different
   choices.
2. **Choosing re-runs the analysis.** The result stays one snapshot of one
   source revision. The alternative — grafting a newly analyzed subtree onto a
   finished result — would produce a map whose parts describe different moments.
3. **Choices are part of the run's configuration**, like limits. Re-analysis,
   Analyze from Here, and opening a saved flow all keep the current choices.
4. **Choices are visible and removable**, listed in the UI with their target,
   and clearing one re-runs without it.
5. **A chosen continuation never looks proven.** This is the rule the feature
   lives or dies by:
   - the node keeps the dispatch confidence it had — a choice does not make an
     ambiguous call exact;
   - the card carries an explicit mark that its continuation was chosen;
   - the details panel names what was chosen and by whom (the reader, not the
     analyzer);
   - every export repeats it.
6. **A choice that no longer applies is dropped, and the reader is told.** If the
   chosen implementation is gone after an edit, re-analysis reports the call as
   ambiguous again rather than silently continuing somewhere else.

## 5. Export: shared rules

Both formats obey the same contract.

1. **Deterministic.** The same result produces byte-identical output, so an
   exported flow can be committed and diffed.
2. **Complete about uncertainty.** Whatever the canvas discloses, the export
   discloses: dispatch confidence, execution mode, project boundaries, cycles,
   depth limits, node-budget truncation, control flow that is not represented,
   and every dispatch choice in effect.
3. **Bounded by the result, not by the canvas.** Collapsed frames are exported;
   what the reader has expanded is a view state, not part of the flow.
4. **No absolute paths.** Locations are project-relative, for the same reason
   stored entries are (`IMPLEMENTATION_GUARDRAILS.md` §13).
5. **Exports carry source-derived text** — condition summaries, branch labels,
   returned expressions — because they are on the map. That is the reader's
   own code going to the reader's own clipboard; it is not logging.
6. **Available only for a result**, and disabled while a run is in progress: a
   partial map exported as if it were whole would misinform.

## 6. Markdown export

A document, not a data format. Structure:

```markdown
# purchase()

`OrderController` · java · depth 3 · 69 nodes · completed

- **load()** — `OrderController`
- **save()** — `OrderController`
  - **audit()** — `OrderController`
- **charge()** — `Gateway` ⚠ ambiguous, chosen: `StripeGateway.charge()`
  - **callApi()** — `StripeGateway`
- **trim()** — `String` — outside the project
- if `flag`
  - **then**
    - **express()** — `OrderController`
  - **else** — nothing

## Not followed

- 5 calls not entered: depth limit
- 2 calls could not be resolved

## Dispatch choices

- `Gateway.charge()` → `StripeGateway.charge()` (chosen by the reader)
```

Rules:

- nesting mirrors frames and branch sections;
- a marker is a word, not a symbol, because a document is read rather than
  scanned;
- the "Not followed" section is the same set of reasons the status area shows
  (`V0.3_SPEC.md` §7.3), omitted entirely when there is nothing to report.

## 7. Mermaid flowchart export

```text
flowchart TD
  n0["purchase()"]
  n1["load()"]
  n2["charge()<br/>ambiguous — chosen"]
  n0 --> n1
  n1 --> n2
```

Rules:

1. **Node ids are positional and stable** (`n0`, `n1`, …) so the diagram diffs
   cleanly; labels carry the names.
2. **Labels are escaped.** A generic type, a quote, or a `>` in a condition
   summary must not break the diagram.
3. **A structure becomes a subgraph** with its sections inside it, so a branch
   reads as a branch rather than as a straight line.
4. **Uncertainty is in the label and the edge style**: a conditional or
   non-deterministic step uses a dashed edge, matching the canvas rule that such
   a connector never claims "this runs next".
5. **A cycle is an edge back to the node it repeats**, not a duplicated subtree.
6. **Size is bounded by the node budget**, so an exported diagram is at most the
   ~100 nodes an analysis can produce.

## 8. Acceptance cases

| # | Case | Expected |
|---|---|---|
| A | An interface call with two implementations | both listed, deterministic order |
| B | An interface call with no implementation in the project | reported as none, no choice offered |
| C | An implementation without a body, or in a library | not offered |
| D | More candidates than the cap | list bounded and says it is partial |
| E | Choosing a candidate | analysis re-runs and the flow continues into it |
| F | A chosen call | still shows its original dispatch confidence, plus a chosen mark |
| G | Two calls to the same interface method | both follow the choice |
| H | Clearing a choice | re-runs, and the call is a dead end again |
| I | Choice plus depth limit | the chosen continuation obeys the same limits |
| J | The chosen implementation is deleted, then re-analysis | reported ambiguous again, choice dropped |
| K | Export a flow with an ambiguous call and a choice | both the ambiguity and the choice appear |
| L | Export twice without re-analysis | byte-identical |
| M | Export a truncated result | the truncation is stated |
| N | Export with collapsed frames | the collapsed content is present |
| O | Mermaid label containing `"`, `<`, `>` | escaped, diagram still valid |
| P | Mermaid export of a flow with branches | sections appear as subgraphs |
| Q | Mermaid export of a flow with a cycle | an edge back, not a duplicated subtree |
| R | Export while a run is in progress | unavailable |
| S | Markdown export of a clean flow | no "Not followed" section |
| T | Any export | no absolute paths |

## 9. Known limitations introduced by v0.4

To be recorded in `KNOWN_LIMITATIONS.md` when implemented:

1. A dispatch choice applies to a callable, so two call sites of the same
   interface method cannot be given different choices.
2. Choices are not persisted; they last for the session.
3. Candidates come from declarations the IDE can find. Runtime substitution —
   dependency injection, proxies, reflection, service loaders — is invisible, so
   a listed candidate is not evidence that it runs, and an empty list is not
   evidence that nothing does.
4. The candidate list is capped, and a project with very many implementations
   shows part of it.
5. A Mermaid diagram of a deep flow is wide; the export does not lay it out or
   paginate.
6. Markdown and Mermaid are the only formats. Sequence diagrams and a structured
   context format are deferred, per §2.
