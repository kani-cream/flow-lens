## 2. The one capability v1.0 added

Scoped after the first real-project run, with the owner's reason stated plainly:
**わかりづらいものは使いたくない.**

`V1.0_GROUPING_SPEC.md` has the semantics. In short: a run of three or more
consecutive library calls that were not entered, sharing one container,
collapses into a single card that names the library and the count, opens to show
its members, and **claims one node against the budget instead of one each**.

### 2.1 What made it necessary

Two entry points in a real Go service, at the default limits:

| Entry point | Nodes | External | The reader's own code |
|---|---|---|---|
| `router.New()` | 100 (truncated) | 90 | 10 |
| `AuthHandler.Login()` | 100 (truncated) | 41 | 59 |

`New()` registers 76 routes. The map drew 76 `RouterGroup.GET()`/`POST()` cards,
spent its whole budget on calls it never entered, and showed none of the 73
handler functions — the only thing a reader wants from a router. It was
truthful and useless, which is the one thing v1.0 could not ship.

### 2.2 The reasoning that was not obvious

The obvious fix is to hide library calls, and it breaks the other entry point.
In `Login()` ten of the forty external calls *are* the story — `ShouldBindJSON`,
`QueryRowContext`, `CompareHashAndPassword`, `SignedString`, `SetCookie`, `JSON`
— and thirty are plumbing. `ShouldBindJSON` and `len` are both external, both
not followed, and one is essential.

**External is not the discriminator; repetition is.** That is what the rule
collapses, and it is why a single library call still gets a card of its own.

### 2.3 What it did to the case that produced it

`router.New()`, same project, same default limits:

| | Before | After |
|---|---|---|
| Nodes | 100 | **37** |
| Result | **truncated** | **completed** |
| The reader's own code | almost none | `NewRateLimiter` ×2, `RateLimitMiddleware` ×2, `AuthMiddleware`, `AdminMiddleware` ×2 — each with its body |
| Disclosure | "outside the project: 90" | "outside the project: **110**" |

The disclosure count went *up* while the card count fell by two thirds, which is
the property the rule was supposed to have: the repetition is gone and none of
the calls are.

The budget going back to the analysis is what made the difference. The
`{ } → Use()` callback — a header middleware with a condition and a `Next()` —
had never appeared at all before, because ninety unenterable route registrations
exhausted the budget first.

**An unplanned property, worth keeping.** A route registered with an inline
closure does not collapse, because the callback event breaks the run. So routes
whose handler is visible stay visible, and routes that are only a reference fold
away. That was not designed; it falls out of adjacency, and it is the right
behaviour.

## 2.4 The node budget, measured rather than assumed

The default was 100 from Milestone 0, where it was the size a feasibility demo
laid out quickly — not a limit anyone had reached. The first real project reached
it at once.

| Measurement | Value |
|---|---|
| `AuthHandler.Login()` to completion | **157 nodes** |
| `router.New()` to completion (after grouping) | 37 nodes |
| Layout at 100 / 300 / 800 / 1200 nodes | 3.0 / 2.4 / 9.4 / 13.1 ms |
| Cards at the root frame for that 157-node result | **22** |

Two things follow. Layout was never the constraint — it has about two orders of
magnitude of headroom — and **node count is not reading effort**: a frame's
children are collapsed, so 157 nodes is 22 cards on screen and the rest appear
only when opened.

The default is 250: comfortably above the measured handler, far below any
rendering cost, and adjustable by anyone who needs more. What grows with the
budget is analysis time, not the size of the wall.

## 4. Defects found before the milestone closed

1. **A group was counted as an external call as well as its members.** A run of
   three reported "outside the project: 4". The first end-to-end assertion of
   the status summary caught it, because the case was written to check the
   number rather than the presence of a line. Both the status area and the
   export now count members and skip the group.

2. **A group would have reported as a structure.** `isStructure` was
   `branches.isNotEmpty()`, which a group satisfies — and a structure's branches
   are *alternatives*, so a group of three would have been drawn as a choice
   between three calls and marked conditional. `isStructure` now asks the kind
   as well, and `BranchKind.GROUP` is not conditional: every member runs.

## 5. Localization

`plan/LOCALIZATION.md` was added during the Japanese pass. It holds the glossary
and, more usefully, the reasoning: why 呼び出し元 is reserved for `caller`, why
展開 may only describe the display control, and why `callable` is named by its
cases rather than translated literally.

The sweep that produced it ran on three axes across the whole bundle rather than
only on the four sites found by reading, and turned up six more. The English
side carried the same staleness and was corrected with it.

## 6. Not verified here

- **Production IDE.** The ZIP has still not been installed into a real IntelliJ
  IDEA Ultimate. It is the last item on the release checklist by the owner's
  ordering, and it remains the go/no-go blocker.
- **Scale.** The grouping rule was measured against one Go service. How it
  behaves on a large Java or Kotlin codebase — where the container is a class
  rather than a package, so runs are shorter — is unmeasured.
- **`UNKNOWN` timing frequency.** Still unknown in practice, and it is what
  decides whether the documented-API list (`KNOWN_LIMITATIONS.md` §39) is the
  right size.
- **The limitations review.** Fifty entries have accumulated; reading them as a
  set — which are still true, which are now fixable, which need saying more
  clearly in the UI — has not been done.
