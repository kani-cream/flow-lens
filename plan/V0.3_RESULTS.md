## 2. What v0.3 added

- **Durable identity** built from the symbol key the analyzers already produce
  plus a project-relative path. Resolution walks the file and asks each analyzer
  to describe the callables it supports, so it stays language-neutral rather
  than needing a lookup API per language.
- **Flow Pins** as a persistent mark on a callable, drawn wherever that callable
  appears, including inside branch sections and on the entry.
- **Saved Flows** carrying the limits their run used, so opening one reproduces
  that analysis instead of re-running it under current settings.
- **Recents**, written only when a run produced a map, capped at ten, kept in
  the workspace file so a list that reorders every few minutes does not produce
  a commit-worthy diff for a team.
- **Analyze from Here**, resolving the conflict recorded in `V0.1_TASKS.md` §1.
- **A run that accounts for itself**: the callable being analyzed, budget
  consumption, and a summary of why the map stops, where each count selects the
  first card it describes.

## 5. Defects found before the milestone closed

1. **Recording a recent deadlocked the run that produced it.** The entry's path
   was derived on the publishing path, inside a read action, while the caller
   was blocked waiting for that very result. The first analysis recorded and the
   second hung. The path is now resolved when the run starts, on the caller's
   thread, so finishing a run touches no PSI at all.
2. **An acceptance suite passed in isolation and failed in the full build.** The
   light project is shared across test classes, so every analysis any other
   suite had run was already in the recents list. The suite now starts from a
   known state rather than assuming one. This is the same shape as the v0.2
   progress-contract defect that CI caught: a test that reads shared state has
   to say what it expects that state to be.
3. **The status strip's single-row invariant.** Adding the reasons row broke the
   regression test that keeps the summary on one line — correctly, since the
   layout was double-counting row height. The summary now takes whatever the
   reasons row leaves, so hiding the reasons restores the original geometry
   exactly, and both properties are test-locked.

### Found by review

4. **Opening the Flows popup parsed every stored file on the EDT.** Ten recents
   plus pins plus saved flows, each a full parse and a walk of every PSI element,
   every time the menu opened. The menu now does a VFS lookup only; the expensive
   resolve happens on activation for the one entry chosen.
5. **"Analyze from Here" was never disabled.** The action had no `update()`, so
   it was offered for external, unresolved, and body-less targets, then silently
   did nothing — or started a run that failed with "no entry point". Analyzability
   is now recorded during the run, so the command is disabled from a map lookup.
6. **Status reasons pointed into collapsed frames.** A depth-limited call is by
   definition at the depth limit, so its link could never select anything. The
   canvas now opens the frames on the way to the node.
7. **Pinning refused nothing.** A placeholder key for an unresolved call, a
   compiler-generated member, or a file outside the project could all be stored —
   the last putting an absolute machine path into a shared file. Pinning now
   round-trips the key through the resolver and refuses what will not come back.
8. **Smaller ones**: the store listener was not released on dispose, so it
   retained the disposed Swing tree; the stores were mutated from the analysis
   coroutine and read from the EDT with no synchronization; the budget bar had no
   label, which is the one thing §7.2 requires of it; and menu rows keyed only by
   symbol collapsed two entries that share a key.

### Found by CI

9. **Stop could cancel the wrong run.** `startAnalysis` leaves the previous run's
   job in the field until the new one is adopted, so a Stop arriving in that
   window cancelled a run that had already finished while the new one carried on.
   CI failed on it twice — the first fix only covered the case where no job was
   present at all. The field is now cleared when a new run is registered, and a
   cancel that arrives before the job exists is remembered and applied on
   adoption. Both windows are test-locked.

   The test was also asserting on a race it had set up, cancelling at the very
   first frame operation, which is inside that window by construction.

10. **A recent is written after its result is published**, so a test reading the
    list the instant the result arrived could miss it. The contract is that a
    finished run becomes a recent, not that both become visible at the same
    instant, so the tests wait for the write rather than assuming it has landed.

## 6. Decisions recorded

- A **Flow Pin marks a callable**, not a call site or a canvas node. The owner
  chose this over an in-flow reading aid; it is also what the plan's requirement
  for durable identity across refactors implies, since a reading aid would need
  no persistence at all.
- **Saved Flows and "persistent saved entry points"** in `PLAN.md` §17 are one
  feature, not two.
- **Neither Saved Flows nor Recents persist a result.** A result describes one
  source revision and is stale as soon as the file changes, so they store the
  entry point and re-run it.
- **The requested progress bar shows budget consumption**, because an
  exploration has no knowable total. The caveat was stated before building and
  the owner asked for the bar anyway; this is the honest form of it.

## 7. Sandbox verification

Performed on 2026-08-18. Confirmed by hand: pinning and unpinning, a pin showing
in a second flow, saved flows and their limits, recents, Analyze from Here, the
progress line, and the stop-reason links.

One gap came out of it, in the samples rather than the product: no callable was
shared between two roots, so a pin could not be seen in a second flow at all —
the procedure was unverifiable as written. `Audit.record()` is now called from
both `Pins.demo()` and `OrderController.purchase()`, and twice within
`Pins.demo()`, once inside a branch.

## 8. CI usage

Four runs for one test, which is three more than the work needed. The second and
third found real product bugs in Stop, so the runs produced value — but they were
only required because the first fix was pushed as a hypothesis rather than a
conclusion. The failure was reproducible locally, and the two windows in
`startAnalysis`/`cancelActive` could have been enumerated together.

Recorded as a rule in `IMPLEMENTATION_GUARDRAILS.md` §18: reproduce locally,
enumerate before fixing, rerun from scratch, review, then push once.
